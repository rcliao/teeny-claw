### Key Findings

**NanoClaw** (~500 LOC core):
- Single Node.js process, SQLite for state, WhatsApp I/O
- Per-group message queue with global concurrency limit (GroupQueue)
- Container isolation: each group runs Claude Code in Apple Container/Docker
- IPC via filesystem (JSON files in ipc/{group}/input/)
- Streaming output via sentinel markers in stdout
- Session = folder. Each group has its own CLAUDE.md, filesystem, container
- Cursor-based message tracking with rollback on error
- Idle timeout → close container stdin → container exits
- No structured context passing between groups — they're fully isolated

**PicoClaw** (~2K LOC core, Go):
- Message bus pattern (InboundMessage → AgentLoop → OutboundMessage)
- ContextBuilder assembles system prompt: identity + bootstrap files + skills summary + memory context + tool summaries
- Session manager: JSON files, in-memory map with mutex, summary field for compaction
- Tool loop: iterate LLM calls up to maxIterations, handle tool calls inline
- Subagent support via spawn tool (no sub-sub-agents)
- Very similar to OpenClaw but ~10x simpler
- Bootstrap files: AGENTS.md, SOUL.md, USER.md, IDENTITY.md (same pattern)
- Skills: summary injected, full SKILL.md read on demand (same pattern)

### Orchestration Patterns Comparison

| Aspect | OpenClaw | NanoClaw | PicoClaw |
|--------|----------|----------|----------|
| Language | TypeScript | TypeScript | Go |
| Context | Rich system prompt + injected files + tool schemas | CLAUDE.md per container | System prompt + bootstrap files |
| Session | JSONL + in-memory | SQLite + container state | JSON files + in-memory map |
| Queue | Lane-based FIFO, per-session + global | Per-group queue + global concurrency | Message bus, single consumer |
| Parallelism | Sub-agents on dedicated lane | Container per group | Subagent manager |
| Isolation | Optional sandbox (Docker) | Mandatory containers | Workspace restriction |
| Memory | Markdown + vector search | CLAUDE.md per group | MEMORY.md + daily files |
| IPC | sessions_send RPC | Filesystem JSON | Message bus (in-process) |
| Compaction | LLM summarization + memory flush | None (Claude Code handles) | LLM summarization |

### What Matters for teeny-claw Orchestration

The core orchestration loop is surprisingly simple across all three:
1. **Receive message** (from channel/bus/queue)
2. **Build context** (system prompt + history + tools)
3. **Call LLM** with tool definitions
4. **Execute tools** inline, append results
5. **Loop** until LLM stops calling tools or max iterations
6. **Save** session state
7. **Send** response

The hard parts are:
- **Context construction** — what goes in, what gets truncated, how to prioritize
- **Queue/concurrency** — serializing per-session while allowing cross-session parallelism  
- **Memory persistence** — surviving compaction, cross-session recall
- **Tool result routing** — getting output back to the right place

For teeny-claw's CLI tools, the orchestration layer would be much simpler:
- No channels/messaging (it's CLI)
- No real-time streaming needed
- Tools are external binaries, not in-process functions
- Context = prompt template + relevant data from other tools
